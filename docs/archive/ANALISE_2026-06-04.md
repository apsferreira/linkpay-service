# Análise — linkpay-service

**Data:** 2026-06-04 | **Categoria:** prod | **Tipo:** auditoria holística single-agent | **Baseline:** sem baseline (primeira auditoria)

---

## Resumo executivo

O linkpay-service é um serviço Go 1.24/Fiber com arquitetura coerente — bounded context bem definido (extração do checkout-service via ADR-003), queries SQL parametrizadas em 100% das operações críticas, JWT assinado com HMAC validado corretamente e migrations sequenciais (001–008). Os maiores riscos são: (1) **cobertura de testes de 2,7%** — muito abaixo da meta de 80%, com handlers, repository e subscription_service sem cobertura alguma; (2) **inconsistência de comissão** entre código (10%) e migration 002 (30%), silenciosa em produção; (3) **CORS wildcard em produção** (`CORS_ORIGINS=*`) e ausência de rate limiting no checkout público; (4) **zero OpenTelemetry** — nenhum trace/metric/span, violando obrigatoriedade para prod; (5) **DownloadZip não verifica o download_count antes** de stremar, permitindo bypass do limite via endpoint `/zip`.

## Arquitetura

**Forças:**
- Bounded context claro e bem documentado no CONTEXT.md — linkpay-service não possui tabela `tenants`, não emite NF-e, não gerencia identidade.
- Separação handler/service/repository/domain respeitada sem vazamentos de camada.
- Interfaces definidas para injeção de dependência (`LinkPayRepoInterface`, `LinkPayPublisher`, `EmailSender`) — testabilidade correta no service.
- Migration 007 (`creator_configs`) com ownership correto: `pix_key` e `payout_schedule` no linkpay-service em vez do checkout-service (ADR-003 respeitado).
- Upsell/cross-sell (migration 008) com FK correta e cascade.

**Gaps:**
- Nenhuma ADR formal documentada em `docs/decisions/` (exigência R5). ADR-003 mencionado apenas no CONTEXT.md e migration.
- `WithPayoutService` e `WithSubscriptionService` são injetados opcionalmente mas não são chamados em main.go — os handlers de payout e subscription recebem `nil` para esses serviços no handler de webhook. Confirmado: `NewLinkPayHandler` não recebe payout/subscription service, e `main.go:106-108` não chama `.WithPayoutService()` nem `.WithSubscriptionService()`. O webhook de TRANSFER_COMPLETED e SUBSCRIPTION_DELETED nunca procesará nada.

## Backend & Segurança

**Forças:**
- Todas as queries SQL usam `$N` (prepared statements via pgx) — sem SQL injection.
- JWT validado com `golang-jwt/v5` verificando método HMAC (`jwt.SigningMethodHMAC`).
- `generateSecureToken()` usa `crypto/rand` (64 chars hex) — correto.
- Webhook usa `hmac.Equal` para comparação constant-time (evita timing attack).
- Graceful shutdown implementado com `os.Signal`.
- Body limit de 150 MB para uploads, validação de tamanho adicional em `UploadProductFile`.

**Gaps:**
- **P0 BLOCKER:** `DownloadZip` não verifica `download_count >= download_limit` antes do streaming. A chamada a `service.Download()` (que incrementa o contador) ocorre **depois** do `c.SendStream(pr)` — se o send falhar ou se o stream já foi iniciado, o produto é entregue sem contar (ou contando mas já entregue). Pior: não há checagem do limite antes de iniciar, apenas incremento.
- **P1:** Validação de webhook Asaas é comparação direta (`hmac.Equal` de secret vs token), não HMAC-SHA256 sobre o corpo. A Asaas usa `asaas-access-token` como token estático — a implementação atual está correta para o modelo Asaas, mas não valida integridade do payload.
- `CORS_ORIGINS=*` no default e `.env.example` — em prod deve ser restrito ao domínio do frontend.
- `SecurityHeaders()` e `NewRateLimiter()` implementados mas não registrados no app (main.go).
- `admin` group (linha 164-172 main.go) usa `authMiddleware` mas não `RequireRole("admin")` — qualquer usuário autenticado acessa balance, payouts, anticipation e stats de outros tenants se souber o endpoint.

## Testes

**Cobertura medida: 2,7%** (22 testes em 12 packages — todos no nível domain/service unit).

**Forças:**
- Testes de domain: comissão, holdback, antecipação — lógica financeira central coberta.
- Testes de service: CreateProduct (default limit, explicit limit), Download (limite, expirado, não confirmado, sucesso + incremento), ProcessPaymentConfirmed (idempotência, charge desconhecido, publica evento).
- Mocks bem estruturados com interface — `mockRepo` e `mockPublisher` reutilizáveis.

**Gaps:**
- Handler layer: zero testes. Rotas como `HandleWebhook`, `InitiatePurchase`, `DownloadZip` sem cobertura.
- Repository: zero testes de integração. Queries complexas (`GetSalesStats` com 3 queries, `GetEligiblePurchases`) não testadas.
- PayoutService: zero testes — código que movimenta dinheiro real (Asaas Transfers) sem cobertura.
- SubscriptionService: zero testes — `Subscribe`, `RenewSubscription`, `CancelSubscription` sem cobertura.
- Middleware: zero testes para `JWTAuth`, `RateLimiter`, `ServiceAuth`.
- CI `continue-on-error: true` nos jobs test e run-tests — pipeline cego a falhas de teste.

## DevOps

**Forças:**
- K3s deployment com resource limits definidos (128Mi/256Mi RAM, 50m/200m CPU).
- Readiness e liveness probes configurados.
- ArgoCD auto-sync mencionado no CONTEXT.md.
- CI com Go 1.24, build multi-stage Docker (alpine builder + alpine runtime).
- Image tag por SHA (`sha-XXXXXXX`) após build.

**Gaps:**
- `continue-on-error: true` em ambos os jobs críticos do CI — testes e lint são decorativos, não gates.
- Sem `gosec`, `govulncheck`, `golangci-lint` no CI — apenas `make lint` mencionado no Makefile.
- Migration sem ferramenta formal: `make migrate` com loop psql sem controle de versão.
- Container roda como root (sem `runAsNonRoot: true` no deployment).
- `securityContext` ausente no K8s deployment (`allowPrivilegeEscalation`, `readOnlyRootFilesystem`).
- `replicas: 1` — sem HPA, sem PodDisruptionBudget. Restart durante deploy causa downtime.
- Imagem fixada em `main-latest` no manifesto inicial, mas CI atualiza para SHA — risco de race condition se ArgoCD sincronizar antes do CI atualizar.

## Dados

**Forças:**
- Pulse client implementado e chamado em 2 eventos (`produto.criado`, `venda.realizada`).
- `GetSalesStats` retorna period, total_revenue_cents, total_sales, produtos e daily_sales — base para dashboard de criador.

**Gaps:**
- Apenas 2 eventos Pulse de 8+ eventos de negócio relevantes: `download.realizado`, `assinatura.criada`, `assinatura.cancelada`, `payout.solicitado`, `antecipacao.solicitada`, `produto.desativado`, `arquivo.upload`.
- North Star (GMV e take rate) não tem pipeline de agregação — stats são calculados on-demand sem materialização.
- `GetSalesStats` fixo em 30 dias sem parâmetro configurável — criador não consegue ver dados históricos além de 1 mês.
- Sem índice em `digital_purchases(created_at)` independente — queries de stats fazem full scan no tenant.

---

## Produto

**Forças:**
- Fluxo completo de venda digital: produto → checkout → webhook → download token → download/ZIP.
- Assinaturas com planos múltiplos (A/B/C), trial, renovação via webhook, cancelamento.
- Antecipação D+2 com taxa de 2% — diferencial competitivo vs Hotmart (D+15).
- Upsell/cross-sell via `product_upsells` + integração com cart-service.
- Múltiplos arquivos por produto com streaming ZIP.

**Gaps:**
- `product_upsells` (migration 008) sem endpoint de CRUD para o criador — admin não consegue gerenciar upsells via API.
- Sem página de obrigado pós-compra (order bump) — apenas download token via email.
- Sem suporte a cupom de desconto.
- Sem affiliate/co-producer split (recorrente em plataformas Hotmart-like).
- Stats fixos em 30 dias sem granularidade configurável.
- Subscriber files (subscription) retorna apenas 1 arquivo do produto principal — múltiplos arquivos de assinatura não implementados em `GetSubscriberFiles` (subscription_service.go:302).

## IA

**N/A (não implementado):** Nenhuma integração LLM/RAG/embeddings no serviço.

**Oportunidades identificadas:**
- **Geração de descrição de produto:** LLM ao criar produto via `POST /api/v1/linkpay/products` pode sugerir/completar `description` a partir do `name` e `product_type` — reduz atrito do criador.
- **Detecção de fraude em checkout:** score de risco por CPF+email+velocidade de compra antes de chamar Asaas — evita chargebacks custosos.
- **Upsell inteligente:** embeddings de produtos para sugerir upsells semanticamente relevantes em vez de tabela `product_upsells` manual.
- **Auto-tagging de produto:** classificar `product_type` automaticamente (ebook/course/template) pelo nome/descrição.

## Compliance/LGPD

**Gaps:**
- CPF armazenado em plaintext em `digital_purchases.customer_cpf` e `digital_subscriptions.customer_cpf` — dado sensível (CPF = dado pessoal sensível na LGPD) sem pseudonimização.
- CPF exposto em resposta JSON da API (campo `customer_cpf` em `DigitalPurchase` com `json:"customer_cpf,omitempty"`).
- Sem endpoint de exclusão de dados do comprador (direito à eliminação, Art. 18 LGPD).
- Sem endpoint de portabilidade (Art. 18, inciso V LGPD).
- Sem registro de consentimento/base legal documentada para coleta de CPF.
- `customer_email` em `digital_purchases` retornado para quem tem o `access_token` — minimização ausente.
- Sem política de retenção de dados definida — `digital_purchases` acumula indefinidamente.
